## Existing authority and extension seams

`MwaSessionHost` owns the pinned walletlib `LocalScenario.Callbacks` for observable authorize, reauthorize, deauthorize, sign_messages, sign_transactions, and sign_and_send_transactions. `get_capabilities` has no host callback in walletlib 2.0.7 and no event will be invented. The host captures a `ProtocolEventHandle` before work, and `PersistentProtocolRecorder` writes one terminal `ProtocolEvent` through `SessionRepository` and Room. `ProtocolEvidenceStore` is a historical process-local compatibility mirror; the Room event is canonical. `ProtocolEvent.injectedFaultId` and `protocol_events.injected_fault_id` already exist.

`LabAuthorizationPolicy` and `NetworkPolicy` keep authorization and Devnet-only decisions. `ApprovalCoordinator` owns explicit human APPROVE/REJECT and cancellation. `LegacyTransactionCodec` parses and signs only supported legacy transactions through `LabSigningService`; `PreApprovalTransactionInspection` is read-only. `DevnetRpcGateway.isBlockhashValid` is the real blockhash check. `SignAndSendSubmissionExecutor` owns real submission and confirmation ordering. Phase 5 `TransactionSimulationCoordinator` and its child Room evidence remain diagnostic only; PASS never approves, FAIL never rejects, and simulation never signs or submits. No fault is implemented by damaging that subsystem.

`MwaLabComposition` is the process singleton wiring seam. A private preferences-backed `FaultSelectionRepository` is the sole selected-fault authority and exposes `StateFlow`. The selected ID is the only persisted fault state; no walletlib request, payload, token, or key is stored. The host captures an immutable profile snapshot at each observable callback start. Each request carries that snapshot through its own hooks. Changing selection changes the next request only. Selection remains across Activity/process recreation; unknown persisted values resolve to NORMAL. No external activity, intent, or provider can set it.

`MainActivity` has Home/Sessions/Detail navigation and can add Fault Lab without replacing navigation. `MobileWalletAdapterActivity` displays `SigningApprovalScreen` from `ApprovalCoordinator.state`; the pending request can carry a display-only snapshot ID. Session cards/detail read canonical `SessionSummary.events`. The demo client has Phase 2/4/5 runners and test transaction factories; Phase 6 scenarios extend that harness, while wallet-side selection remains manual in production.

## Catalog and wire contract

Method abbreviations: A = AUTHORIZE, R = REAUTHORIZE, M = SIGN_MESSAGES, T = SIGN_TRANSACTIONS, S = SIGN_AND_SEND_TRANSACTIONS. All failure rows mean `ProtocolOutcome.FAILURE`, `ProtocolFailureSource.INJECTED`, and `injectedFaultId` equal to the stable ID. The UI must display “INTENTIONAL TEST CONDITION” for an applied fault. The persisted event keeps truthful request metadata, error code, source, ID, timing, and sanitized result. Those same structured fields are available to a future Phase 7 report, but no exporter is added here. Choosing another profile or NORMAL resets selection for subsequent requests; existing events never change.

The unsupported-chain wire callback uses walletlib’s legacy “cluster” wording while the request summary keeps the actual incoming chain, including a valid Devnet request. Reauthorization uses its observed callback only; internally rejected tokens are never fabricated as events. The sign-and-send invalid vector uses the pinned callback’s `completeWithInvalidSignatures` name. NORMAL user rejection has `ERROR_NOT_SIGNED` but `OBSERVED_PROTOCOL` and a null ID; numeric error codes never establish injection.

## Engine, recorder, and cancellation contract

The pure engine evaluates `(captured profile, method, hook)` and returns Continue or one typed decision. It has no Activity, Compose, walletlib request, signing service, parser, or RPC dependency. Host adapters call the engine at explicit hooks, check existing authorization/session/validation preconditions, and translate a decision through the already-used pinned callbacks. A decision is marked on the pending recorder handle when actually applied, before the synthetic callback or delay. One event accepts the same ID repeatedly, rejects a different second ID, and rejects annotation after terminal claim. An INJECTED terminal failure without a valid ID is forbidden at the recorder and Room write boundary. Cancellation/association replacement settles the original event once and retains an already marked ID; the old generation cannot sign, submit, or mutate a replacement session.

Delay is `kotlinx.coroutines.delay(5000)` on a request coroutine, never a blocking sleep. Closing/replacing a session cancels the pending approval and invalidates generation; an old delayed continuation rechecks generation and authorization before approval/signing. A delayed later success is SUCCESS/NONE with the delay ID. A delayed later manual rejection is FAILURE/OBSERVED_PROTOCOL with the delay ID. Selection itself is not event evidence: a profile with unmet preconditions or an unrelated method leaves the event ID null. A nonterminal annotation may coexist with a different terminal source.

Room schema 3, historical migrations/schemas, walletlib 2.0.7, Devnet-only safeguards, Phase 5 simulation authority, and Phase 4 parser/signing boundaries remain frozen. Phase 7 Markdown/JSON export and Share Sheet are out of scope.
